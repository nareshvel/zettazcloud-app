# Role-Based Access Control (RBAC) and Subscription Management Overview

## Overview

This document outlines the Role-Based Access Control (RBAC) system with a two-tier permission system and subscription management designed for the Zettaz Cloud multi-store architecture. The RBAC system will provide flexible, granular, and scalable access control across the platform while supporting the multi-tenant and multi-store structure.

## Business Requirements

1. **Multi-store Support**: Users should be able to have different roles and permissions across different stores
2. **Tenant-level Access Control**: Support for tenant administrators who can manage all stores
3. **Customizable Roles**: Ability to create and modify custom roles with specific permission sets
4. **Granular Permissions**: Fine-grained control over system functionalities
5. **Hierarchical Structure**: Permission inheritance from tenant to store level
6. **Subscription-based Features**: Support for different subscription plans with varying feature access
7. **Usage Limits**: Enforce limits based on subscription plan (stores, users, etc.)
8. **Platform Administration**: System-level roles for managing the entire platform
9. **Audit Trail**: Track permission changes for security and compliance

## System Architecture

The system consists of two primary components: Role-Based Access Control and Subscription Management.

### RBAC System - Two-Tier Architecture

#### Platform Level (System)

1. **System Permissions**
Platform-wide capabilities managed by system administrators (e.g., "manage tenants", "view platform stats")

2. **System Roles**
Collections of system permissions for platform administrators (e.g., "Super Admin", "Support", "Billing Admin")

3. **User System Role Assignments**
Associations between users and system roles that apply platform-wide

#### Tenant Level

1. **Tenant Permissions**
Individual capabilities within a tenant's domain (e.g., "view products", "create orders")

2. **Tenant Roles**
Collections of permissions that can be assigned to users (e.g., "Admin", "Store Manager", "Cashier")

3. **Scopes**
The context in which roles apply:
- **Tenant Scope**: Applies across all stores within a tenant
- **Store Scope**: Applies only to specific store(s)

4. **User Role Assignments**
The association between users, roles, and scopes, defining what a user can do and where

### Subscription Management

1. **Plans**
Defined subscription tiers with specific features, limits, and pricing (e.g., "Basic", "Professional", "Enterprise")

2. **Features**
Functional capabilities enabled by subscription plans

3. **Usage Limits**
Quantitative restrictions based on subscription tier (e.g., number of stores, users, transactions)

4. **Subscriptions**
The association between tenants and plans, including lifecycle management (trial, active, expired, etc.)

## Database Schema

The system uses the following tables:

### Platform Level (System)

1. **system_permissions**: Defines platform-level permissions
2. **system_roles**: Defines roles that can be assigned to platform administrators (stored in `roles` table with NULL `tenant_id` or in a separate `system_roles` table)
3. **system_role_permissions**: Maps system permissions to system roles
4. **user_system_roles**: Associates users with system-level roles (may use the same `user_roles` table with appropriate flags)

### Tenant Level

1. **permissions**: Defines permissions available across the platform
2. **roles**: Defines tenant-specific roles with non-NULL `tenant_id` 
3. **role_permissions**: Maps permissions to both system and tenant roles
4. **user_roles**: Associates users with roles in specific scopes (tenant or store)

### Role and Permission Relationships

1. **Role Types**:
   - **System Roles**: Global roles that apply across all tenants (e.g., "Super Admin", "Platform Admin")
   - **Tenant Roles**: Roles specific to a tenant (e.g., "Store Manager", "Cashier")

2. **Role Scope**:
   - **Tenant Scope**: Role applies to all stores within a tenant
   - **Store Scope**: Role applies only to specific store(s) within a tenant

3. **Permission Inheritance**:
   - Users can have both system and tenant roles simultaneously
   - When retrieving roles and permissions, both system roles (tenant_id IS NULL) and tenant-specific roles are included
   - Store-scoped roles take precedence over tenant-scoped roles with the same name

### Subscription Management

1. **plans**: Defines subscription plans with features and limits
2. **subscriptions**: Tracks tenant subscriptions with status and lifecycle data

## Key Benefits

- **Flexibility**: Create custom roles with specific permission sets
- **Granular Control**: Assign permissions at tenant or store level
- **Multiple Store Support**: Users can have different roles at different stores
- **Scalability**: Easy to add new permissions as the application grows
- **Security**: Principle of least privilege can be properly implemented
