# Proxy Implementations for RBAC Services

## Overview
As part of the RBAC consolidation strategy, we've implemented proxy services to ensure backward compatibility while we transition to the new consolidated RBAC system. This document outlines the approach, implementation details, and timeline for the complete transition.

## Implementation Approach

### Proxy Pattern
We've used the proxy pattern to transparently forward all calls from the legacy services to the new consolidated `rbacService.js`. This allows us to:

1. Maintain backward compatibility with existing code
2. Display deprecation warnings to developers
3. Gradually transition all code to use the new consolidated service
4. Allow for safe, incremental migration without breaking changes

### Services Proxied
The following services now act as proxies to the consolidated `rbacService.js`:

1. **userRoleService.js** - Manages role assignments for both system and tenant-level roles
2. **userRbacService.js** - Handles fetching and checking permissions and roles

## Deprecation Strategy

### Warning Mechanism
When a deprecated service is called, it logs a warning only once per server instance to avoid flooding logs:

```javascript
function logDeprecationWarning() {
  if (!deprecationWarningLogged) {
    logger.warn('DEPRECATED: serviceX.js is deprecated and will be removed in a future release. Use rbacService.js instead.');
    deprecationWarningLogged = true;
  }
}
```

### Developer Experience
Developers using the legacy services will see deprecation warnings in the logs, encouraging them to update their code to use the new consolidated service directly.

## Migration Timeline

### Phase 1: Proxy Implementation (Completed)
- Create the consolidated `rbacService.js` with all functionality from both legacy services
- Implement proxy forwarding in legacy services with deprecation warnings
- Update core middleware to use the consolidated service directly

### Phase 2: Code Migration (In Progress)
- Update all routes to use the consolidated service directly
- Update migration scripts and utils to use the consolidated service
- Update any frontend service calls to use the new API endpoints

### Phase 3: Removal (Scheduled for September 2025)
- Remove the proxy implementations entirely
- Complete documentation updates
- Final code cleanup

## Testing Considerations

### Unit Tests
Unit tests have been created for the consolidated `rbacService.js` to ensure all functionality works as expected before and after the migration.

### Integration Testing
Integration tests should be updated to use the consolidated service directly, though the proxy implementations will continue to work during the transition period.

## Best Practices for Developers

### For New Code
Always use the consolidated `rbacService.js` directly:

```javascript
const rbacService = require('../services/rbacService');

// Check if user has permission
const hasPermission = await rbacService.hasPermission(userId, 'some.permission', tenantId);
```

### For Existing Code
Update code to use the consolidated service when making other changes to a file:

```javascript
// Before:
const userRoleService = require('../services/userRoleService');
await userRoleService.assignTenantRole(...);

// After:
const rbacService = require('../services/rbacService');
await rbacService.assignTenantRole(...);
```

## Rollback Plan
If issues are discovered with the consolidated service, we can temporarily modify the proxy implementations to revert to their original implementation while maintaining the same interface.
