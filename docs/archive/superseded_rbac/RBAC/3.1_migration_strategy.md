# Migration Strategy: Legacy to Two-Tier RBAC System

## Overview

This document outlines the strategy for migrating from our legacy permission system to the new two-tier Role-Based Access Control (RBAC) system in the Zettaz Cloud platform. The migration should be approached carefully to maintain backward compatibility while gradually transitioning to the more powerful and flexible two-tier system.

## Current vs. New Permission Systems

### Legacy Permission System
- **Format**: Simple string format (e.g., `'grn:create'`, `'inventory:read'`)
- **Structure**: Flat hierarchy with no scope distinction
- **Implementation**: Direct permission checks in middleware
- **Database**: Single-table approach for permissions

### New Two-Tier RBAC System
- **Format**: Hierarchical dot notation (e.g., `'inventory.grn.create'`, `'products.view'`)
- **Structure**: Two-tier system with system-level and tenant-level permissions
- **Implementation**: Scope-aware permission checks with subscription validation
- **Database**: Separate tables for system and tenant permissions with role mappings

## Migration Roadmap

### Phase 1: Planning and Preparation (1-2 weeks)

1. **Complete Permission Mapping**
   - Document all existing permissions
   - Define corresponding new permissions
   - Create a formal mapping document

2. **Update Permission Constants**
   - Add new permission constants in `permissionMiddleware.js`
   - Maintain legacy constants for backward compatibility

3. **Enhance Permission Middleware**
   - Implement support for both permission formats
   - Add mapping logic for transparent conversion

### Phase 2: Database Schema Updates (1 week)

1. **Run Schema Migration**
   - Ensure all new RBAC tables are created
   - Add required indices for performance

2. **Create Data Migration Scripts**
   - Script to create new permission records
   - Script to map roles to new permissions
   - Script to migrate user role assignments

### Phase 3: Core Service Implementation (1-2 weeks)

1. **Implement New Services**
   - Permission service
   - Role service
   - User role service
   - Subscription service

2. **Update Authentication Flow**
   - Enhance token generation to include roles/permissions
   - Add subscription data to tokens

### Phase 4: Route Migration (2-4 weeks)

1. **Incremental Route Updates**
   - Prioritize routes by criticality and usage
   - Start with low-risk, less frequently used routes
   - Progress to core functionality gradually

2. **Testing and Validation**
   - Unit test both permission formats
   - Integration test critical workflows
   - Load test permission-heavy operations

### Phase 5: UI Updates (1-2 weeks)

1. **Admin Interface Updates**
   - Add role management UI
   - Add permission assignment UI
   - Add subscription management UI

2. **User Interface Updates**
   - Implement permission-based UI rendering
   - Add subscription feature indicators

### Phase 6: Finalization (1 week)

1. **Legacy System Deprecation**
   - Remove legacy permission support
   - Clean up old code paths
   - Update documentation

### 3. Route Migration Example

```javascript

router.route('/')
  .post(hasPermission(PERMISSIONS.GRN.CREATE), createGrn)
  .get(hasPermission(PERMISSIONS.GRN.READ), getGrns);

router.route('/')
  .post(hasPermission(PERMISSIONS.TENANT.INVENTORY.GRN.CREATE), createGrn)
```

## Testing Strategy

1. **Unit Tests**
   - Test both legacy and new permission formats
   - Verify permission mappings work correctly
   - Test subscription checks

2. **Integration Tests**
   - End-to-end workflow testing
   - Test with various user roles
   - Verify subscription enforcement

3. **Performance Tests**
   - Measure impact of enhanced permission checks
   - Optimize database queries if needed

## Rollback Plan

In case of critical issues:

1. **Quick Rollback**
   - Return to legacy permission middleware
   - Keep dual permission structure in database

2. **Data Integrity**
   - Ensure all migrations preserve original permission data
   - Maintain separate IDs for new permissions

## Conclusion

This migration strategy provides a path from our legacy permission system to the new two-tier RBAC system with minimal disruption to users. By maintaining backward compatibility during the transition, we can methodically migrate different parts of the application while maintaining system stability.

The migration should be approached incrementally, with thorough testing at each stage. Regular communication with development teams about the migration status is essential to ensure all new code uses the appropriate permission format.
